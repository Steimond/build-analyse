# Product Backlog

Этот репозиторий создаёт полезные инструменты для Unity Editor с распространением через Unity Asset Store. Цель — выпускать самостоятельные продукты, которые решают реальные проблемы разработки, а со временем складываются в общую линейку.

## Принцип работы

Не выбирать «единственный продукт навсегда». Каждая идея остаётся в бэклоге до момента, когда мы готовы начать её разработку. Тогда отдельно проверяем актуальный рынок: похожие ассеты в Asset Store, open-source решения, обсуждения Unity-сообщества, отзывы пользователей, цены и незакрытые сценарии. После этого подтверждаем, что идея всё ещё оправдана, и определяем её позиционирование.

Первый продукт: **Build Diff**.

## Направление линейки

Основная линия — **Doctor Tools**: инструменты диагностики Unity-проектов. У продуктов будут общие принципы работы: понятные отчёты, приоритизация проблем, безопасные quick-fix действия и возможность запускать проверки из CI.

```text
Project Doctor
├── Build Doctor
├── Addressables Doctor
├── UI Performance Doctor
├── Performance Doctor
└── Mobile Doctor
```

Общий актив линейки — движок правил. Каждая проверка должна быть изолированной, проверяемой и пригодной для повторного использования. С ростом набора правил повышается ценность всей линейки и снижается стоимость следующих продуктов.

## Первый продукт — Build Diff

### Проблема

После новой сборки размер приложения увеличился, но Unity не объясняет, что именно добавило эти мегабайты. Разработчику приходится вручную сопоставлять отчёты, папки и зависимости.

### Обещание пользователю

Build Diff сравнивает два артефакта сборки или их отчёта и показывает, что изменилось: например, «сборка выросла на 37 МБ; основной вклад внесли такие-то ассеты, пакеты или файлы».

### Первый MVP

- Выбор базовой и новой сборки или отчётов сборки.
- Сравнение итогового размера и списка файлов.
- Сортировка изменений по абсолютному приросту размера.
- Разделение на добавленные, удалённые и изменившиеся элементы.
- Понятный отчёт, который можно сохранить или передать команде.
- Работа локально, без обязательного облака и без отправки данных проекта.

### Вопросы перед реализацией

- Какие форматы отчётов Unity стабильно доступны в поддерживаемых версиях редактора?
- Поддерживаем ли первый релиз только Android, или также Windows/macOS/iOS?
- Сравниваем готовые сборки, Build Report, AssetBundle/Addressables layout или несколько источников?
- Какой отчёт полезнее всего: окно в Editor, HTML, CSV, JSON для CI?
- Какие существующие продукты уже закрывают этот сценарий и где у них слабые места?

### Границы первого релиза

Не пытаться сразу сделать полноценный анализатор размеров, оптимизатор импорт-настроек или Addressables-инспектор. Первая версия должна надёжно отвечать на один вопрос: **что изменилось между двумя сборками и насколько это повлияло на размер**.

## Приоритет после Build Diff

Следующими кандидатами для проверки рынка считаются Project Doctor, Build Size Analyzer, Addressables Doctor, Release Preflight и UI Performance Doctor. Порядок не зафиксирован: его определяют рыночная проверка, сложность реализации и возможность повторно использовать код из Build Diff.

## Принципы качества

- Объяснять проблему и её причину, а не только выводить технические данные.
- Не изменять проект без явного действия пользователя; для исправлений показывать последствия.
- Поддерживать воспроизводимые результаты и экспорт отчётов.
- Делать основу продукта полезной без внешнего сервиса.
- Сохранять архитектуру готовой к переиспользованию в следующих инструментах линейки.
